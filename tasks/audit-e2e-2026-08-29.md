## 2. New findings

### E1 ⚠️ **Starting a session took 49.9 seconds.** *(demo-day risk)*

Measured end to end through the real route, on this machine:

```
POST /start-attendance  ->  200 {"session_id":3,"success":true}   49.9 s
```

Broken down by direct measurement:

| Stage | Cost |
|---|---|
| `import recognize_face` | 1.86 s |
| `load_model_and_labels()` — trainer.yml is **72 MB** | **8.80 s** |
| Camera acquisition (fallback scan; camera 1 alone blocked **17.9 s**) | ~35 s |
| MediaPipe FaceMesh construction | the remainder |

The camera cost is the *fallback* path — `open_best_camera()` step 2 takes the
saved preference and skips the scan when that device is healthy, so a demo
machine with a good saved camera pays much less. **But the fallback is exactly
what runs when the saved camera is held by another application, unplugged, or
wedged** — the moment you least want a minute of silence. `/cameras` measured
**11.3 s** on its own, on the request thread, with no progress indication.

There is nothing to fix here before the demo. There is something to *know*:
press Start early, and do not press it twice.

⚠️ **This scales badly and it is the same curve as todo.md §7 Q1.**
`trainer.yml` is 18 MB per identity. At 4 identities the model takes 8.8 s to
load at session start; at 30 students it would be ~540 MB and roughly a minute
of load *before* the camera is even opened, on top of the 280–400 ms per face
per frame already recorded. **This is new evidence for Q1, which is the
user's decision.**

### E2 ⚠️ **B4 confirmed end to end: a frozen camera returns `success: true`.**

The morning's audit inferred this. It is now driven and observed. In the same
run as E1, the application logged:

```
WARNING camera_utils: Camera 2 returned 9 identical frames - this is probably
        a still image or a stopped virtual camera, not a live feed.
INFO    camera_utils: Opened camera 2 (..., FROZEN)
WARNING camera_utils: Using camera 2, which appears to be a still image
```

...and then `/start-attendance` returned **`{"success": true}`**, and
`/attendance/live` reported `{"running": true, "recognised": 0}`. The verdict
is computed, logged, and thrown away before the response is built
(`web/sessions.py`, `start_attendance` → `start_camera`). The operator's screen
says the session is running. It is running against a photograph.

**Confirm the feed moves before calling the first student.** The fix — carry
the `frozen` flag into the response — is small, but it touches the session
start path and should not be made the week of a defense.

### E3 **The accuracy figure has a stray identity in it, and the table prints a fake 0%.** *(Q&A risk)*

`eval_heldout_accuracy.py` reproduces **80/80, 100.00%, avg 33.46** exactly.
Its per-student table reads:

```
Student: 12345         | Held-Out Accuracy:   0.00% (0/0)
Student: 23-1-1-0559   | Held-Out Accuracy: 100.00% (20/20)
Student: 23-1-1-0918   | Held-Out Accuracy: 100.00% (20/20)
Student: 23-1-1-0920   | Held-Out Accuracy: 100.00% (20/20)
Student: test-111      | Held-Out Accuracy: 100.00% (20/20)
```

Two problems on one screen:

1. **`test-111` is not a person.** It is a test folder with no `students` row.
   So "100% across four identities" is really **three students and one test
   fixture**, and the fixture contributes 20 of the 80 correct answers — a
   quarter of the headline number.
2. **`12345` prints `0.00% (0/0)`.** An empty folder divided by zero, rendered
   as a student the system never once recognised. A panel member reading down
   that column sees a 0% row. The `(0/0)` is the tell, and it is small.

Neither is a code defect — both are the dataset showing through. Clean
`dataset/` on the demo machine and re-run the evaluator, then quote *that*
number with its date. The four caveats in the docstring (same-session split,
near-duplicate frames, no impostor set, no FAR) remain the honest part and are
unaffected.

### E4 **`subjects.day` is stored, edited, displayed — and never enforced.** *(low)*

`day` is written by `repositories/subjects.py` and shown in the UI. Nothing
reads it. CS401 is scheduled **Monday**; today is **Saturday**, and a session
started and ran normally. Harmless for the demo — and a fair panel question
("what does the day column do?") with no good answer. Say it is metadata for
the timetable and not a gate, rather than being caught out by it.

### E5 **Doc drift: `capture_dataset.py` is documented as deleted and is not.** *(low)*

`docs/benchmarks.md:242` records it as **deleted**. It is present, 43 KB, and
still runs a **full camera capture session at module scope** — window
creation, `cv2.imshow`, camera open, and `sys.exit()` — so importing it opens
a camera. This is one of the two "executes on import" traps `CLAUDE.md` warns
about, and it is real.

*Correction to handover 6e §7*: it attributes the "deleted" claim to
`docs/limitations.md`. The claim is in `docs/benchmarks.md`;
`docs/limitations.md` does not mention the file.

### E6 **This working copy had no runnable environment at all.** *(process)*

Neither installed interpreter could run the project: Python 3.11 was missing
Flask, pytest, mediapipe, numpy **and** opencv-contrib (its `cv2` was a broken
partial install with no `__version__`); Python 3.9 had only numpy and
opencv-contrib. **Nothing in this tree could be executed as found.** Every
number in §1 was produced against a venv built for this audit at `C:\aa-venv`.

Two things worth carrying:

- ⚠️ **`pip install -e ".[dev]"` fails under a long path** — it died with
  `OSError: [Errno 2] No such file or directory` on a deeply-nested numpy
  `f2py` test file until the venv was moved to `C:\aa-venv`. The error names
  a Fortran test fixture and not the real cause, which is Windows MAX_PATH.
  Anybody rebuilding this on a fresh machine will hit it and will not guess
  why. **Install to a short path.**
- The venv at `C:\aa-venv` is left in place — it is outside the project and
  is currently the only way to run anything here. Delete it freely; rebuild
  with `python -m venv C:\aa-venv` then
  `C:\aa-venv\Scripts\python -m pip install -e ".[dev]"`.

## 4. Before the demo — in order

Fifteen minutes, and preflight scores it for you.

1. **Add every student to a class list.** Manage Students → Classes column;
   anything reading "None" needs adding. *Without this the demo fails.*
2. **Move CS401's start time to just after your slot.** `derive_status()` has
   no grace period; one second past the minute is Late.
3. **Delete `dataset/test-111/` and the `12345` student**, then retrain.
   On a machine that retrains every release, a stray folder comes back every
   release.
4. **Add one instructor account.** Role separation is enforced correctly
   (verified, §1) and can otherwise only be described, not shown.
5. **Run one full session** so Reports and the Excel export have history.
6. **Re-run `eval_heldout_accuracy.py`** on the cleaned dataset and quote that
   number, with its date (G2).
7. **`python scripts/preflight.py --subject <id> --cameras`** — it must exit 0.
8. **Do not deploy in the hour before** (D5: a session started mid-retrain runs
   on the old model), and **`mysqldump` first** if the update carries a
   migration (D6: DDL cannot roll back).
9. **On the day:** press Start early (E1), and **confirm the picture is moving
   before calling the first student** (E2).

Also still true and worth rehearsing: liveness is a two-pose challenge and is
replay-defeatable (G1) — claim *raised effort*, never anti-spoofing; there is
no password reset (G6); logout does not end a running session (G10).
